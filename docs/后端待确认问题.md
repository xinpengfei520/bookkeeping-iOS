## 问题一：外币记录改回人民币时，`/book/detail/update` 会清空那三个字段吗？

### 背景

对接说明 3.2 节写明：

> ⚠️ 注意：一致性校验目前**只在新增（save）时生效，更新（update）不校验**。

客户端严格遵守了「三个字段要么全给、要么全不给」的规则。于是出现一个文档没有覆盖的场景。

### 具体场景

用户先记了一笔美元账，随后编辑这笔账、把币种改回人民币（金额也改成人民币金额）。

**改之前**，库里这条记录是：

```jsonc
{
  "bookId": 10518,
  "price": 35.11,            // 人民币
  "currency": "USD",
  "originalPrice": 5.20,
  "exchangeRate": 6.752650
}
```

**客户端发出的 update 请求**（按「全不给」规则，三个字段不出现在请求体里）：

```json
POST /book/detail/update
{
  "bookId": 10518,
  "year": 2026, "month": 8, "day": 3,
  "price": 25.50,
  "mark": "午饭",
  "categoryId": 1
}
```

### 需要确认的

上面这个请求打过去之后，库里的 `currency` / `original_price` / `exchange_rate` 三列会变成什么？

| 可能的行为 | 结果 | 我们的判断 |
|---|---|---|
| A. 三列被置为 NULL | ✅ 数据正确：这就是一条普通人民币记录 | **期望是这个** |
| B. 三列保持原值不变 | ❌ 脏数据：`price=25.50` 但 `currency=USD, originalPrice=5.20, exchangeRate=6.752650`，`price ≠ originalPrice × exchangeRate`，且这条人民币记录会一直带着 USD 标记 | 需要修 |

因为 update 不做一致性校验，如果是 B，服务端不会报任何错，客户端也无从感知 —— **会静默留下自相矛盾的记录**，之后查询接口把这三个字段返回给 APP，APP 会把它当外币记录展示（显示成 `US$5.20`），与用户实际填的人民币金额对不上。

### 如果当前行为是 B，我们能接受的任一方案

1. **（首选）后端在 update 时按「未提供即清空」处理** —— 与 save 的「全不给 = 人民币记账」语义一致，客户端零改动。
2. 后端支持客户端显式传 `null` 来清除，例如 `{"currency": null, "originalPrice": null, "exchangeRate": null}` —— 请告知这样传是否会被参数校验拦掉（`currency` 有 `^[A-Z]{3}$` 的格式校验，不确定 null 是否豁免）。
3. 新增一个显式字段，如 `"clearCurrency": true`。

选 2 或 3 的话客户端改一行就行，只要明确告诉我们传什么。

### 附带的小建议

同一节里提到「如果你们希望后端在更新时也强制校验，请反馈」—— **我们希望加上**。理由：客户端已经保证了 `price = round(originalPrice × exchangeRate, 2)`，但一旦客户端出 bug 或有第三方调用，update 这条路径现在是完全没有防护的，脏数据会直接落库且无人察觉。加上校验后，客户端反而能通过 4001 及时发现自己的问题。

## 问题二：登录密码的传输与存储方案

### 现状（客户端）

登录、改密都是**明文密码走 HTTPS**，没有做任何客户端哈希：

```json
POST /book/user/login
{ "loginType": "password", "phone": "138xxxxxxxx", "password": "明文密码" }
```

```json
POST /book/user/password/update
{ "phone": "138xxxxxxxx", "oldPassword": "明文旧密码", "password": "明文新密码" }
```

> 补充说明：iOS 工程里有一个历史遗留的 `md5` 字符串分类，但**全工程零调用**（已确认是 fork 带来的死代码），客户端确实没有在做任何哈希。

### 需要确认的

**服务端是怎么存密码的？**

| 方案 | 是否可接受 |
|---|---|
| bcrypt / argon2 / scrypt（带盐、慢哈希） | ✅ 现代标准，无需改动 |
| PBKDF2 + 足够迭代次数 | ✅ 可接受 |
| SHA-256 加盐 | ⚠️ 可用但不理想，建议迁移 |
| MD5 / SHA-1，或不加盐 | ❌ 建议尽快迁移 |
| 明文存储 | ❌ 必须改 |

### 我们的看法

**"明文传输 + 服务端慢哈希" 本身是正确做法**，业界主流（含各大银行 App）都是这样，前提是：

- 全链路强制 HTTPS（已满足）
- **服务端用慢哈希 + 每用户独立盐存储**

所以我们**不打算**在客户端加哈希 —— 客户端哈希其实是安全反模式：哈希值会变成"等效密码"，一旦库泄露，攻击者直接拿哈希值就能登录，反而削弱了服务端慢哈希的意义。

**因此这个问题的核心只有一句话：请确认服务端的密码存储用的是哪种算法。** 如果已经是 bcrypt/argon2，那这条就此关闭，客户端不需要任何改动。

### 如果需要迁移

推荐渐进式，无需强制用户改密：

1. 用户下次登录成功时（此时能拿到明文密码），用新算法重新哈希并覆盖旧记录
2. 记录一个 `password_algo` 字段标识当前用哪套
3. 校验时按 `password_algo` 分派，老算法验证通过后立刻升级
4. 存量全部迁移完毕后再下线老算法

这个过程客户端**完全无感、零改动**。
