记账 App · 后端接口需求文档

语音智能记账解析接口

POST /book/parse
版本 v1.0 日期 2026-08-14 关联功能 语音记账 M2 优先级 高
01

接口说明

客户端语音记账流程分两层解析。第一层是端上规则解析器（已上线），覆盖"打车 35 块""昨天午饭花了二十八"等典型短句，响应在 10ms 内。当规则解析器未能识别金额（price = 0）或类别（categoryId = -1）时，客户端调用本接口作为第二层兜底，由服务端借助 LLM 完成语义理解并补全缺失字段。

客户端对本接口设置 2 秒硬超时——超时后直接使用规则解析结果弹出确认卡片，不阻塞用户操作。因此服务端必须在 2 秒内响应。

扩展预告：M3 多图 OCR 记账将复用本接口（text 传 OCR 识别文本），详见第 9 节预留设计。
02

鉴权

与现有全部接口一致，使用两个固定请求头：

Header示例值说明
AuthorizationBearer eyJhbGci…用户 JWT，格式固定为 Bearer <裸 token>
app_id638c2977f1b24ba0固定值，标识 iOS 客户端

JWT 过期时返回 code: 5001，客户端会自动跳转登录页（与现有其他接口行为一致）。

04

响应

成功响应示例

{
  "code": 0,
  "msg": "success",
  "data": {
    "price": 60.00,
    "categoryName": "餐饮",
    "isIncome": false,
    "date": "2026-08-13",
    "mark": "和老王吃饭",
    "confidence": 0.86
  }
}

data 字段说明

字段类型必返说明
pricenumber必须人民币金额，正数，保留两位小数。无法确定时返回 0
categoryNamestring必须类别名，如 "餐饮"。无法确定时返回 ""（空串，不要省略字段）
isIncomeboolean必须true=收入，false=支出
datestring可选格式 YYYY-MM-DD。无法确定时不返回该字段，客户端保留自身的规则解析日期
markstring可选提炼的备注，最长 20 字。无法确定时不返回
confidencenumber必须置信度 0.0–1.0，仅供后续统计/优化，客户端不依赖此值决策
重要：date 和 mark 字段——无法确定时请不要返回该字段（而非返回 null 或空串）。客户端的合并策略是"只补全缺失字段"，若服务端总是返回这两个字段，客户端无法区分"LLM 有结果"与"LLM 返回了默认值"。

失败响应示例

{
  "code": 400,
  "msg": "text 不能为空",
  "data": null
}
05

业务逻辑与 LLM 建议

调用链路

接口收到请求后的建议处理流程：

  1. 校验 text 非空且 ≤ 500 字符，否则返回 400
  2. 构造 prompt，调用 LLM（建议超时设为 3–5 秒，给客户端的 2 秒硬超时留足 buffer）
  3. 校验 LLM 输出合法性（price > 0、date 格式正确），剔除非法字段
  4. 按响应格式组装并返回

推荐 LLM 与 Prompt

记账话术是短文本字段提取，DeepSeek-V3 / 通义千问等轻量模型完全够用，单次调用成本极低。以下 prompt 供参考：

你是一个记账助手，从用户的一句话中提取记账字段。
只返回 JSON，不要有任何解释文字。

今天日期：{today}   （用于计算"昨天""前天"等相对日期）

用户输入：{text}

返回格式（无法确定的字段按规则处理，见注释）：
{
  "price": 数字或0,           // 无法确定返回 0
  "categoryName": "类别名",   // 无法确定返回 ""
  "isIncome": true或false,
  "date": "YYYY-MM-DD",       // 无法确定则【不包含此字段】
  "mark": "备注",             // 无法确定则【不包含此字段】
  "confidence": 0.0到1.0
}

categoryName 用中文，从以下常用分类中选择最匹配的（可以是其他合理分类）：
餐饮、交通、购物、日用、水果、蔬菜、零食、运动、娱乐、通讯、
服饰、美容、住房、居家、社交、旅行、烟酒、数码、医疗、书籍、
学习、信用卡、礼物、亲友、维修、快递、工资、兼职、理财、报销、
退货、出售、红包

字段提取规则参考

字段提取规则
price提取句中金额，统一换算为人民币元，保留两位小数；"六十多"取整数部分（60）；无法确定返回 0
categoryName从语义匹配最合适的类别；"打车/滴滴/地铁"→交通，"午饭/外卖"→餐饮；无法确定返回 ""
isIncome命中"工资/报销/收到/退款/卖了"等词→true，否则 false
date解析"昨天"→今天-1，"8月3号"→年份取今年；无法确定则不返回该字段
mark剔除金额/日期/口语填充词后剩余的动宾短语（如"和老王吃饭"），≤20字；无法提取则不返回
06

错误码

codemsg 示例含义客户端行为
0success成功使用 data 补全缺失字段
400text 不能为空参数校验失败（text 为空或超长）降级用规则解析结果
401unauthorizedJWT 缺失或格式错误降级用规则解析结果
5001token_expiredJWT 已过期自动跳转登录页（与全局逻辑一致）
500server_error服务器内部错误（含 LLM 调用失败/超时）降级用规则解析结果

非 0 的业务错误码，客户端统一降级用规则解析结果，不会向用户展示错误信息。

07

性能要求

指标目标值说明
P50 响应时间≤ 1.2 秒大多数请求应远低于客户端超时
P99 响应时间≤ 1.8 秒客户端硬超时 2 秒，需留 200ms buffer
服务端 LLM 超时3–5 秒LLM 超时后服务端返回 500，客户端已降级
接口限流30 req/min/user防止异常调用；正常记账频率远低于此值
关键约束：客户端 2 秒超时是硬性的，超时后 LLM 响应会被客户端丢弃。建议服务端将 LLM 调用超时设置在 1.5 秒以内（含网络往返），否则会白白消耗 LLM 额度。

09

扩展预留：M3 多图 OCR 记账

M3 计划让用户长按 + 号选择相册，对账单截图进行 OCR 后批量记账。OCR 文本结构复杂，将强依赖本接口的 LLM 能力，复用路径如下：

  • 客户端 OCR 识别账单截图，得到多行文本，拼接后通过 text 字段传入
  • 服务端 LLM 需要从中解析出多条记账记录

为此，建议本期接口设计时在请求体中预留 mode 字段（可选，默认 "single"），以便 M3 上线时无需新增接口：

// M3 请求示例（本期无需实现，仅预留字段）
{
  "text": "2026/08/13  星巴克  38.00\n2026/08/13  滴滴出行  23.50",
  "mode": "multi"
}

// M3 响应示例（data 变为数组）
{
  "code": 0,
  "msg": "success",
  "data": [
    { "price": 38.00, "categoryName": "餐饮", "isIncome": false, "date": "2026-08-13", "mark": "星巴克", "confidence": 0.92 },
    { "price": 23.50, "categoryName": "交通", "isIncome": false, "date": "2026-08-13", "mark": "滴滴", "confidence": 0.95 }
  ]
}

本期（M2）只需实现 mode 缺省时的单条解析逻辑，M3 排期后再补充 multi 分支。
