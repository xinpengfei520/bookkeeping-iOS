# 语音记账 —— 方案设计（动手前梳理）

> 日期：2026-08-13
> 状态：**M1 已完成（v1.0.19，2026-08-13）**；M2/M3 待排期

---

## 一、一句话目标

**长按首页 + 号 → 说一句"昨天打车花了三十五块八" → 松手 → 弹确认卡片（金额 35.8 / 类别 交通 / 日期 昨天 / 备注 打车）→ 点确认 → 走现有落库管线。**

全程目标 3 秒内完成一笔记账，比打开键盘手输快一个数量级。

---

## 二、结论先行：要不要后端配合？

**v1 完全不需要后端。** 三个环节全部可以在端上免费完成：

| 环节 | 端上方案 | 是否免费 | 是否需要网络 |
|---|---|---|---|
| 语音 → 文字（ASR） | Apple `Speech` 框架（`SFSpeechRecognizer`，zh-CN） | ✅ 系统自带 | 优先端上识别（A12+ 设备）；不支持时自动回退 Apple 服务器识别（需网络，单次 ≤1 分钟，对一句话记账绰绰有余） |
| 文字 → 结构化字段 | **端上规则解析器**（正则 + 中文数字转换 + 类别同义词表） | ✅ | ❌ 纯本地 |
| 落库 | 复用现有 `NOTIFICATION_BOOK_ADD` → `addBookRequest` 管线 | — | 弱网自动进离线队列（1.0.17 已闭环） |

**v2 才需要后端**：规则解析器覆盖不了的复杂话术（"和老王吃饭 AA 了一半付了六十多"）走 LLM 兜底。LLM 必须由后端代理（密钥不能进客户端），接口草案见第六节 —— 但这是**可选增强**，不阻塞 v1。

免费开发者账号无任何限制（Speech/Vision 都不需要特殊 entitlement）。

## 三、交互设计

### 主流程（长按 + 号）

```
按住 + 号
  ├─ 立即：+ 号上方浮出录音卡片（波形动画 + "松开结束，上滑取消"）
  ├─ 说话中：实时显示 ASR 中间结果文字（Speech 支持 partial results）
松开手指
  ├─ 结束录音 → 拿最终文本 → 规则解析（<10ms，无感）
  ├─ 解析出金额 → 弹确认卡片
  └─ 没解析出金额 → 确认卡片金额留空高亮，让用户补（不静默丢弃）
确认卡片（半屏弹层）
  ├─ 顶部：原始识别文本（灰字，可回溯"它听到了什么"）
  ├─ 四个字段：金额（可点开数字键盘改）/ 类别（横向滚动选择器，预选解析结果）
  │            / 日期（默认解析结果，可点开日期选择）/ 备注（可编辑）
  ├─ [确认记账] → 发 NOTIFICATION_BOOK_ADD，卡片收起，首页列表立即出现该笔
  └─ [取消] / 下滑关闭
上滑取消（录音中）
  └─ 手指上滑超过阈值：卡片变红提示"松开取消"，松手直接丢弃
```

### 手势兼容性（已核查代码）

- + 号现有交互是 `UITapGestureRecognizer`（点按打开记账键盘页），**加 `UILongPressGestureRecognizer` 天然共存，零冲突**（`HomeController.m addButton`）。
- 首次长按时依次触发麦克风、语音识别两个系统权限弹窗，之后不再打扰。

### 为什么不复用 BookController 做确认页

看过代码：`BookController` 的编辑态（`setModel:`）走的是 **update** 分支，把解析结果塞进去会发修改请求而不是新增；而且它是全屏页 + 类别网格，交互重心是"人工挑类别"，与"机器已解析、人只需扫一眼确认"的心智相反。**确认页独立做一个轻量半屏卡片**（`VoiceConfirmView`），同时给未来的 OCR 多条确认复用（列表形态）。

## 四、技术选型明细

### 4.1 ASR：Apple Speech 框架（不引第三方）

- `SFSpeechRecognizer(locale: zh-CN)` + `AVAudioEngine` 流式喂音频，`shouldReportPartialResults = YES` 拿实时文字。
- **优先 on-device**（`supportsOnDeviceRecognition` 为真时设 `requiresOnDeviceRecognition`）：无网可用、无配额、隐私好；老设备自动回退 Apple 服务器识别。
- 不选讯飞/火山等第三方的理由：要引 SDK + 密钥 + 计费，而记账话术是短句识别，系统 ASR 准确率完全够；有了 LLM 兜底后差距更小。
- 注意点：`AVAudioSession` 用 `.record` + `.duckOthers`（压低正在放的音乐而不是打断）；录音结束恢复会话；处理来电/Siri 打断。

### 4.2 解析器：端上规则引擎（v1 核心，纯逻辑可单测）

新类 `KKBookTextParser`（Foundation-only，进测试套件），输入一句话，输出：

```objc
@interface KKParsedBookEntry : NSObject
@property CGFloat price;          // 0 表示没解析出来
@property NSInteger categoryId;   // 匹配到的类别，-1 未匹配
@property BOOL isIncome;
@property NSInteger year, month, day;
@property NSString *mark;
@property NSString *rawText;      // 原始识别文本
@end
```

**解析规则（按优先级）**：

1. **金额**：
   - 阿拉伯数字：`35.8`、`35 块 8`、`1,200`
   - 中文数字：`三十五块八` → 35.8、`两百五` → 250、`一千二` → 1200（写一个中文数字转换器，含"两/俩/半"等口语）
   - 单位归一：块/元/毛/角/分（`五毛` → 0.5）
   - 多个数字时取带货币单位的那个；都不带取最后一个
2. **收支方向**：命中"收入/工资/发了/红包/报销/退款/收到" → 收入；默认支出
3. **类别**：两层匹配
   - 第一层：与**本地类别表**（`getCategoryModelList`，含用户自定义类别）做包含匹配
   - 第二层：内置同义词表（打车/滴滴/地铁/公交/加油→交通；早饭/午饭/晚饭/外卖/咖啡/奶茶→餐饮；房租→住房……约 30 组，覆盖高频口语）
   - 都未命中 → categoryId = -1，确认页预选第一个支出类别并高亮提示
4. **日期**：今天（默认）/ 昨天 / 前天 / 大前天 / `N 月 N 号(日)`；相对日期用现有缓存 calendar 计算
5. **备注**：剔除金额、日期短语后的动宾短语（如"打车"）；提取失败就用整句

**质量保障**：解析器配 50+ 条真实话术的单元测试用例表（数据驱动，一行一个 `输入 → 期望字段`），以后遇到解析不准的话术直接加用例再改规则。

### 4.3 多币种

v1 语音只记人民币（口语说"美元"的场景极低频，且汇率确认交互放进语音流程会很重）。确认页可以手动切，但解析器不做外币识别 —— 明确砍掉。

## 六、v2：LLM 兜底解析（唯一需要后端的部分，可后置）

触发条件：规则解析器金额或类别置信度不足，且有网络。

**接口草案**（给后端的，届时再细化成对接文档）：

```
POST /book/parse
{ "text": "昨天和老王吃饭AA我付了六十多" }

← { "code": 0, "data": {
      "price": 60, "categoryName": "餐饮", "isIncome": false,
      "date": "2026-08-12", "mark": "和老王吃饭AA",
      "confidence": 0.86 } }
```

- 后端接 DeepSeek/通义等便宜模型，密钥、限流、计费全在服务端；
- 客户端超时 2 秒：LLM 没回来就直接弹规则解析的结果，**永不阻塞交互**；
- 同一接口将来给 OCR 多图记账（v3）复用："OCR 文本 → 多条记账"只是 prompt 不同。

## 七、v3：多图 OCR 记账（展望，不在本期）

长按 + 号出现"语音 / 相册"两个分支。OCR 本身也是端上免费（Vision `VNRecognizeTextRequest`，iOS 14+ 支持中文），但账单截图文本杂乱，**强依赖 v2 的 LLM 接口**才能做好，所以排在 LLM 之后。确认卡片的多条列表形态在 v1 设计时预留。

## 八、风险与边界

| 风险 | 应对 |
|---|---|
| 模拟器上 Speech 识别不可用/不稳定 | 解析器与确认页均可用文本直接驱动（`KK_DEBUG_OPEN=voice` 后门喂固定文本），录音链路真机验证 |
| 服务器识别模式需要网络 | 无网 + 老设备（不支持 on-device）时长按弹提示"当前设备无网络无法语音识别"，不静默失败 |
| 口音/嘈杂环境识别错 | 确认页永远展示原始识别文本 + 全字段可改；识别文本不自动落库 |
| 权限被拒 | 引导去设置开启；被拒后长按弹权限引导而不是无响应 |
| 长按误触发 | `minimumPressDuration = 0.4s`；松手时录音 < 0.5s 视为误触直接丢弃 |
| 类别是用户自定义的 | 解析器第一层就匹配本地类别表（含自定义），不写死系统类别 |

## 十、待拍板的决策点

1. **v1 先纯端上规则，LLM 兜底放 v2 —— 同意吗？** 我的理由：规则解析对"动词+金额"的典型记账话术命中率很高，先上线收集真实 badcase，再决定 LLM 接口的 prompt 怎么写更有依据；而且 v1 完全不用等后端。
2. **确认卡片 vs 免确认直接落库**：我强烈建议 v1 必须过确认卡片（ASR 会错，静默记错账比慢一步伤害大）。将来可以加个"连续三次未修改自动跳过确认"的渐进优化。同意吗？
3. **LLM 选型（v2 才用到，现在只是预告）**：后端是你自己的 SpringBoot，届时接 DeepSeek（便宜）还是通义/豆包，成本你来定，接口形状按第六节。

确认这三点后我就按 M1 动工。
